# Decisions

**Replay and storage.** The simulator reconstructs 120 environments from the session start time and an append-only reprovision log. Spend accrues only during billable runtime. Production uses Neon Postgres. The app selects configured SQL first, then optional legacy private Vercel Blob, then local files. Postgres uses write-once `INSERT … ON CONFLICT DO NOTHING` on unique keys. Concurrent starts adopt the stored anchor. Concurrent reprovisions of the same environment from the same observed restart count share a key, so only one insert wins. Actions on different environments use distinct keys.

**Refresh and polling.** Each instance caches shared and demo sessions for a configurable refresh window (30 seconds by default via `PERSIST_REFRESH_MS`). Successful writes update that instance’s cache immediately. Other instances discover those actions on refresh, and an insert conflict triggers an immediate refresh. Visible tabs poll every four seconds. Poll responses carry the action log, and the dashboard keeps its current view until a snapshot contains every pending confirmed action by environment ID and timestamp.

**Isolated demos.** The shared workshop is the default. **Start fresh demo** and **Start guided demo** each create a fresh cohort with its own session anchor and action log. The guided flow walks the instructor through the existing simulated reprovision action and reports the observed result. A tab restores its selected demo on reload. Starting another demo preserves existing sessions, and **Return to shared** reopens the shared workshop with its own history. Demos expire after 24 hours.

**Shared view data.** The server derives filtered rows, the full floor map, and aggregates from one replayed cohort and clock per request. The 2D and 3D maps share stable seat assignments, filter results, and Status, Spend, and Progress values. Both keep the full room visible and dim seats outside the filtered results.

**AI failure behavior.** The offline compiler handles canonical filters and rejects invalid or unconsumed constraints before any model fallback. The optional model returns a candidate filter. The route rejects malformed objects and checks recognizable constraints against the original request. This check has limited coverage for free-form language. The instructor sees and confirms the candidate before it applies. Editing or clearing the request cancels pending results. Timeouts, invalid output, or a missing provider leave the manual controls usable.

**What's next.** Next I'd add per-learner history views so progress and spend trends are visible over time, not just current values; instructor-set alerts for learners stuck past a threshold; and wider offline coverage in the plain-English filter so the optional model is needed less. The backend is real today, a live API with durable storage; what stays simulated is the cloud environments and billing behind it. Integrating live Azure provisioning and real accounts is a larger project I deliberately did not attempt here.
